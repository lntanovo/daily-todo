## 0. 部署前必须确认

- **pgcrypto 扩展是否可用**。`20261105120000_reminders.sql` 用 `digest()` 和
  `gen_random_bytes()` 生成配对码与设备 id。缺这个扩展时**创建函数不会报错**，
  要等到第一次配对才 500：

  ```sql
  select extname from pg_extension where extname = 'pgcrypto';  -- 必须有一行
  ```
  没有就先 `create extension if not exists pgcrypto;`。

- `reminder-done` 的卡片按钮依赖飞书自定义机器人对 `interactive` 卡片、URL 按钮的支持。
  先在测试群用一条手工消息验证：卡片能渲染、按钮能在**手机飞书**里打开链接。
  若失败，把云函数环境变量设为 `REMINDER_FEISHU_FORMAT=post`，退化为纯文本 + 链接。
  （注意：自定义机器人的按钮只支持 URL，不支持回调；要"点按钮改期/删除"得走自建应用。）

- 决定 `REMINDER_BASE_URL`：完成链接对外可达的站点地址。
  用现有的 `https://daily-todo-d3gq5mama7a468d02-1485775300.ap-shanghai.app.tcloudbase.com` 即可。

## 3. 部署云函数

三个函数都零依赖，直接用 Node 内置能力：

| 函数 | 触发 | 环境变量 |
| --- | --- | --- |
| `reminder-tick` | SCF 定时触发器（每分钟） | `APP_ENV_ID`、`APP_REGION`、`CLOUDBASE_API_KEY`、`REMINDER_BASE_URL`、`REMINDER_FEISHU_FORMAT`(可选)、`REMINDER_DIGEST_GRACE_MINUTES`(可选)、`REMINDER_PURGE_DAYS`(可选)、`REMINDER_DRY_RUN` |
| `reminder-done` | HTTP `/api/reminder/done` | `APP_ENV_ID`、`CLOUDBASE_API_KEY`、`REMINDER_BASE_URL` |
| `reminder-device` | HTTP `/api/reminder/device/*` | `APP_ENV_ID`、`CLOUDBASE_API_KEY` |

- `CLOUDBASE_API_KEY` 只能放在函数环境变量里，绝不能进前端或仓库。
- **定时触发器**：`cloudbaserc.json` 已为 `reminder-tick` 声明
  `{"name":"reminder-every-minute","type":"timer","config":"0 */1 * * * * *"}`
  （SCF 七段：秒 分 时 日 月 周 年）。
  `tcb fn deploy` **不会**自动创建它，必须单独执行：

  ```powershell
  tcb fn trigger create reminder-tick -e <envId> `
    --trigger-name reminder-every-minute --cron "0 */1 * * * * *"
  ```

  已执行并确认（`tcb fn detail reminder-tick` 的 Triggers 一栏可见）。没有它，
  `reminder-tick` 只是个躺着的函数——所有提醒一条都不会发，而且**不会报任何错**。
- 判断它真的在跑：函数监控里每分钟一次调用；日志里出现 `tick` 事件，
  字段应包含 `digest_am` 与 `digest_pm`。
  ⚠️ 本环境的 CLS 日志服务没开，`tcb fn log` 会报 `topic not exist`。
  在开通日志服务之前，**唯一可信的运行证据是 `todo_reminder_log` 里出现记录**
  （需要先配好 Webhook，见第 5 节），或者用 `tcb fn invoke reminder-tick`
  手动跑一次看返回值里的 `digest_am` / `digest_pm`。
- HTTP 入口按 `cloudbase/operations/reminder-done-gateway.json` 与
  `cloudbase/operations/reminder-device-gateway.json` 配置。
- Rego 策略见 `cloudbase/operations/registration-access.rego`，只额外放行
  `/api/reminder/done` 与 `/api/reminder/device/*`。

1. `REMINDER_DRY_RUN=1`，挂定时器跑满一天。日志只应有 `dry_run` 事件，且 `due` / `digests` 数量符合预期。

   - 同一分钟重复触发不会重复发送（看 `todo_reminder_log`）；
   - **早报与晚间各只发一次**：`select kind, remind_date, channel, status from todo_reminder_log order by claimed_at desc limit 10;`

3. 再验证早报、免打扰（把 `quiet_start` 设成当前时间前后）、删除任务后点击旧链接（应显示「这一项已经删除」）。
4. 最后用两个账号验证隔离：A 的设置和日志对 B 完全不可见，B 收不到 A 的提醒。

## 6. 倒计时 / 逾期 / 晚间收尾的语义

一次汇总最多三段，**折进同一条消息**，不单独推送——否则一条作业会在几天里反复轰炸：

```
📋 11-16 周日 · 今天 2 项
· 15:00 讲座：XX（14:30 再提醒）
· 23:59 交 操作系统作业3

⚠️ 逾期 1 项
· 11-14 交实验报告2（逾期 2 天）

⏳ 倒计时
· 明天 高数小测（11-17 10:00）
· 3 天后 编译原理作业（11-19）
```

| 设置 | 位置 | 默认 | 作用 |
|---|---|---|---|
| `remind_lead_days` | 设置 → 提醒 →「提前几天开始倒计时」 | 3 | 倒计时区块覆盖未来 1—N 天；0 表示只看当天与逾期 |
| `evening_enabled` | 「晚上再提醒一次…」 | 开 | 是否发晚间收尾 |
| `evening_time` | 「晚间收尾时间」 | 20:30 | 晚间档的触发时刻 |

- 早报：今天要做的 + 已逾期 + 倒计时。
- 晚间：**今天还没完成**的 + 已逾期 + 倒计时（标题「今晚收尾（N 项未完成）」）。
- 逾期只判定**单日任务**：某天到期、那天没打勾，且不超过 30 天。重复任务与跨天任务不参与逾期判定（它们的"到期"语义不同，宁可不猜）。
- 跨天任务不进入倒计时，否则一个三周的项目会天天喊"还有 N 天"。
- 两条汇总各用独立账本种类（`digest` / `digest_pm`），同一天互不影响；同一分钟内重复触发由 claim 去重。

验收造数：

```sql
-- 今天到期、三天后到期、两天前逾期，各一条
insert into public.todo_tasks (owner_id, id, title, type, task_date, remind_time)
values (auth.uid(), 't_today', '交作业3', 'single', current_date, '23:59'),
       (auth.uid(), 't_cd3',   '编译原理作业', 'single', current_date + 3, null),
       (auth.uid(), 't_over',  '交实验报告2', 'single', current_date - 2, null);
-- 把早报时间改到两分钟后，等一条消息；再把晚间时间改到两分钟后，等第二条
```

## 7. 已知限制

- 单日与重复任务才单独提醒；连续多日任务只进汇总（避免连续多周轰炸）。
- `remind_time` 为空时回退 `start_time`；两者都为空则只在汇总里出现。
- 每分钟一次的轮询意味着到点延迟最多约 1 分钟。
- 网络抖动最多重试 3 次，超过则记 `failed`，不再发送。
- 提醒日志保留 60 天，过期令牌清理 7 天前的记录。
- 迁移只在**本地一次性 PostgreSQL** 上跑通过（完整链路 11 份迁移 + 18 项断言），
  云端仍需在可回滚的快照上先跑一遍，并核对第 2 节的查询结果。
- 本地验证时 pgcrypto 用桩替代（见第 0 节），云端必须真实存在。
- 本地 `daily-reminder` 的桌面通知读的是 `tasks.md`，与云端任务不是同一份数据；
  要做到「桌面也提醒云端任务」仍需 Phase 1 的 feed 接入（现已支持当天到点项）。
